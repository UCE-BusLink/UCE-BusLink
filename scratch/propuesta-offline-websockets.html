Parte A — 01

Modo Offline-First

Arquitectura de alto nivel

El proyecto ya usa TanStack Query para mutaciones (useUpdateProfile en OnboardingModal) y Zod para validar formularios en el frontend web (route.schema.ts). La propuesta reutiliza ambas piezas en vez de introducir un framework de sincronización nuevo:

  • Capa de lectura (datos de referencia): rutas, paradas, horarios y el perfil del usuario se sirven con staleTime largo vía TanStack Query, persistidos en IndexedDB con @tanstack/query-sync-storage-persister (adaptado a IndexedDB con idb-keyval). Esto cubre "ver mis rutas/horarios sin conexión" para estudiantes y conductores sin escribir una capa de caché manual.
  • Capa de escritura ("outbox"): toda acción que muta estado (crear/cancelar una reserva, reportar posición GPS, cambiar el estado de un viaje) se escribe primero en una tabla IndexedDB local pendingActions, con un actionId (UUID v4) generado en el cliente. La UI se actualiza de forma optimista de inmediato.
  • Vaciado de la cola: un Service Worker (Workbox vía vite-plugin-pwa) usa Background Sync para disparar el envío de pendingActions en cuanto el navegador detecta conexión. Como Background Sync no existe en iOS Safari, se añade un flush manual al recuperar el foco de la app (visibilitychange) como respaldo.

Nota de alcance

Mobile (React Native/Expo) no tiene IndexedDB ni Service Workers nativos: ahí el mismo patrón de outbox se implementa con expo-sqlite o AsyncStorage + un listener de NetInfo en vez de Background Sync. La forma (cola + reconciliación) es la misma; solo cambia el motor de almacenamiento local.

Seguridad: evitar que se sincronicen datos corruptos

  • Doble validación: Zod valida antes de encolar (evita basura local), pero el backend siempre revalida con @Valid al recibir la acción — nunca se confía en que "ya pasó por el cliente".
  • Idempotencia obligatoria: cada acción en pendingActions viaja con su actionId como header Idempotency-Key. El backend guarda claves procesadas recientemente (Redis, TTL de ~24h) y responde con el resultado ya cacheado si la clave se repite — así una reconexión inestable que reenvía la misma acción dos veces no crea una reserva duplicada.
  • Autenticación fresca antes de vaciar la cola: el token de Clerk puede expirar mientras el dispositivo estuvo offline. Antes de reproducir el outbox, se refresca el token (getToken({'{'}template:'uce-buslink'{'}'})); si el refresco falla, la cola se conserva intacta y se le pide al usuario reautenticarse — nunca se reintenta con un token vencido ni se descarta la cola en silencio.
  • Límite de lote: el endpoint de sincronización acepta como máximo ~50 acciones por llamada (paginado), para que un dispositivo con una cola enorme (o un cliente comprometido) no pueda enviar una ráfaga que sature al backend.

Esquema de resolución de conflictos al reconectar

No hace falta un motor de fusión genérico: el dominio ya distingue entre datos de referencia (rutas, paradas) que solo el admin escribe, y acciones puntuales (reservar, reportar GPS) que sí pueden chocar con el estado del servidor.

Parte B — 02

Notificaciones push en tiempo real (WebSockets)

Lo que ya existe (y de lo que hay que partir)

El backend ya corre un broker STOMP completo en tracking-module (WebSocketConfig, endpoint /ws/tracking, JwtChannelInterceptor para autenticar el CONNECT) usado hoy para la posición GPS de los buses. La propuesta es extender ese mismo mecanismo para rutas y viajes, no levantar una segunda infraestructura de mensajería en paralelo.

/topic/trip/{'{'}tripId{'}'}/location-updateexisteGPS + ETA de un viaje puntual
/topic/supervisor/all-busesexistesnapshot de toda la flota cada 5s
/topic/routes/{'{'}routeId{'}'}nuevoruta creada/editada/desactivada
/topic/trips/{'{'}tripId{'}'}/statenuevoviaje reprogramado, cancelado, etc.
Hallazgo al explorar el código

SubscriptionSecurityInterceptor hoy solo valida destinos que empiezan con /topic/trip/. /topic/supervisor/all-buses no tiene ningún chequeo de rol al suscribirse. Al añadir los tópicos nuevos, conviene cerrar también ese hueco existente — cualquier cliente autenticado puede unirse hoy al feed completo de la flota.

Arquitectura: eventos de dominio, no llamadas directas

El proyecto ya tiene el patrón correcto para esto: GpsLocationReceivedEvent y BusApproachingEvent se publican como eventos de Spring (ApplicationEventPublisher) en vez de que tracking-module llame directo a otros módulos. Se propone lo mismo para rutas y viajes:

Cómo evitar saturar el servidor

  • Tópicos segmentados, no un solo canal global. Un estudiante suscrito a /topic/routes/{'{'}routeId{'}'} de su ruta habitual no recibe cambios de las otras 30 rutas — el broker STOMP en memoria ya soporta esto sin trabajo extra.
  • Un evento por operación, no por campo. El wizard de "Crear Nueva Ruta" tiene 3 pasos; el evento RouteChangedEvent se publica una sola vez, al confirmar el paso final (createRoute/updateRoute), no en cada tecla del formulario.
  • Reusar el heartbeat ya configurado (30s/30s en WebSocketConfig) en vez de que cada cliente haga polling — esto ya está resuelto en el proyecto, solo hay que no reintroducir polling en los nuevos flujos.
  • El volumen es bajo por naturaleza: solo administradores escriben rutas/viajes, así que a diferencia del GPS (que llega varias veces por segundo por bus), este canal emite eventos esporádicos — no necesita throttling adicional.

Escalar a más de una instancia de backend

Hoy el broker STOMP es enableSimpleBroker — vive en memoria de una sola instancia de la JVM. Si el backend corre en más de un contenedor (por ejemplo detrás de un load balancer en QA/producción), un cliente conectado a la instancia A nunca ve un evento publicado desde la instancia B.

Recomendación

El proyecto ya usa Redis (hoy solo como caché key-value en TrackingRedisConfig). Se propone añadir un canal de Redis Pub/Sub: cada instancia publica el evento tanto a su SimpMessagingTemplate local como a un canal Redis; un RedisMessageListenerContainer en cada instancia escucha ese canal y reenvía a sus propios clientes STOMP. Es la opción más barata de operar frente a introducir un broker externo completo (RabbitMQ/ActiveMQ) cuando ya se paga por Redis en la infraestructura actual.
